# S-CAM

S-CAM is a fork of the `vault` application as customized for Defcon34 (upstream:
[bunnie/dc34-vault](https://github.com/bunnie/dc34-vault)). The repo is named `s-cam`, but the
crate and the binary it builds are still called `dc34-vault`.

It is a camera badge that also stores credentials: take pictures, scan QR codes, keep FIDO2
passkeys, TOTP secrets and passwords. Upstream's gene-exchange light mixing is cut - see
[What the badge does](#what-the-badge-does).

> [!WARNING]
> Loading your own firmware wipes the light encryption key and puts the badge in developer
> mode. On this line that has already happened: `k0` is zeroed and unrecoverable, which is
> part of why gene exchange was cut. It is a one-way door, so it matters for a stock badge
> you have not yet flashed.

## Building

Assumes the four repos are checked out side by side:

```
 .
 ├── s-cam           <- this repo (the `dc34-vault` app)
 ├── s-cam-api
 ├── s-cam-console
 └── xous-core
```

`xous-core` must be the fork, not upstream: this firmware needs commits that are not in
betrusted-io's tree (the S-CAM USB device name, and the serial back-pressure and retry fixes).
They live on `heckseven/xous-core` at branch `s-cam`, which is that fork's default branch, so
a plain clone lands on it. Recorded here anyway, because the dependency is otherwise invisible
and that fork's `main` is a stale pre-fork artifact that does **not** carry these commits.

All four repos use `s-cam` as their default branch, not `main`.

Prerequisites:

- Latest Rust
- Run `cargo xtask install-toolkit` inside the `xous-core` repo

Then build from this repo:

```shell
./tools/build.sh
```

That builds the console and the vault, checks the app against the 307-page loader limit,
runs the source wiring guards, and bundles the result. Output is `loader.uf2`, `xous.uf2`
and `swap.uf2` under `../xous-core/target/riscv32imac-unknown-xous-elf/release/`.

Do not call `cargo xtask baosec-lite` on its own. xtask bundles whatever app ELFs it is
pointed at; it does not build them, so on its own it will happily package a stale
`dc34-vault` and print a successful-looking build the whole way through. For reference,
`tools/build.sh` runs the equivalent of:

```shell
(cd ../s-cam-console && cargo build --release --target riscv32imac-unknown-xous-elf \
    --features board-baosec --features oem-baosec-lite --features bao1x --features utralib/bao1x)

(cd ../s-cam && cargo build --release --target riscv32imac-unknown-xous-elf --features board-baosec)

(cd ../xous-core && cargo xtask baosec-lite \
    ../s-cam-console/target/riscv32imac-unknown-xous-elf/release/dc34-console~flash \
    ../s-cam/target/riscv32imac-unknown-xous-elf/release/dc34-vault \
    --no-timestamp --feature usb --kernel-feature debug-proc --no-verify)
```

The crate and binary names are still `dc34-vault`, `dc34-console` and `dc34-api`; only the
repo directories were renamed. See [docs/PINS.md](./docs/PINS.md) for the upstream commits
this fork descends from.

## What the badge does

S-CAM keeps upstream's credential storage and adds a camera. The root menu is:

| Entry | What it holds |
|---|---|
| `login deets` | `2fa digits`, `passkeys`, `passwords`, `manage usernames` |
| `qr collection` | saved URLs, which only ever arrive by scanning a QR code |
| `photos` | pictures taken with the badge or uploaded over serial |
| `settings` | `bling`, `blinky`, `screen off` |
| `about` | a QR code pointing at this README |

The camera is the addition. It scans QR codes and it takes pictures, and a stored photo can
be set as the standby image - the panel is 1bpp 128x128, so photos are dithered to match.
Standby shows the S-CAM logo by default, the DEFCON logo if you pick it, or any photo you
have saved.

> [!NOTE]
> **Gene exchange is cut.** Upstream's headline feature - mixing encrypted light patterns
> between badges by scanning each other's QR codes - is not in this fork. `DECISIONS.md`
> records why: it freed four `VaultMode` variants, `genemenu.rs`, and the whole k0 / nonce /
> `DC34_HEADER` path, which bought the size budget the camera UI needed. `defcon-scheme.md`
> is kept as a description of the protocol that used to be here, not of this firmware. LED
> pattern mutation survives; it never touched k0.

## Token Mode

Detached from the badge carrier - two screws on the back of the module, with replacements and
a silicone cap in the badge kit - the module works over USB as a FIDO2 token. It also stores
TOTPs and plaintext passwords, added by scanning QR codes generated by
[this browser extension](https://github.com/baochip/qr-url-extension).

Those QR codes also carry the current time. The device has no battery and no clock across
power cycles, so scan one after plugging in if you want TOTP codes to be correct.

## Serial console

The module enumerates a USB serial port (as `S-CAM`; the bootloader enumerates as
`Baochip-1x`, which is how you tell the two apart). `dc34-console` runs a REPL there. The
commands most worth knowing:

```
photo list          what is stored
photo get <n>       print one photo as text, to be decoded on the host
photo put           write a photo to the badge
upload > upload.py  emit an uploader script, then: python3 upload.py picture.png
```

Host-side helpers in `tools/`:

| Tool | Use |
|---|---|
| `watch-badge.py` | follow the log, reopening the port across crashes and reboots |
| `recv-export.py` | receive one photo export |
| `show-export.py` | render a received export |
| `photo-grab.html` | pull every photo off the badge from a browser |

## Flashing your own build

`tools/flash-queue.sh` flashes a queue of staged builds, verifying checksums first and
confirming the unmount afterwards. A staged build is a directory of `loader.uf2`, `xous.uf2`,
`swap.uf2` and `SHA256SUMS`, with optional `LABEL` and `EXPECT` notes:

```shell
./tools/flash-queue.sh flash-queue/<session>
./tools/flash-queue-verdict.sh flash-queue/<session> <build> pass|fail "what happened"
```

> [!WARNING]
> Always stage a known-good build last, named `99-rollback` or carrying a `ROLLBACK` file.
> The script withholds it unless you pass `FLASH_ROLLBACK=1`, so a normal run flashes only
> what you are testing - but it is there the moment a build does not boot. A build that fails
> to boot loops or hangs, and the only way back is the bootloader.

This badge is sensitive to code layout, not just size. Builds well under the 307-page limit
have boot-looped because of where the linker put things; `check-app-size.py` and
`DECISIONS.md` record the cases. Treat "it compiled and fits" as necessary, not sufficient,
and flash with a rollback staged.

## Updates

Get *stock* firmware updates at [https://ci.betrusted.io/releases/latest/baochip/dc34-badge/latest.zip](https://ci.betrusted.io/releases/latest/baochip/dc34-badge/latest.zip) — this is upstream's build, and flashing it replaces anything built from this fork. The zip file must be extracted into the three constituent files (xous.uf2, swap.uf2, loader.uf2) prior to copying to the device!

To perform an update:

1. Press and hold any button while plugging the module into a computer. This will cause the device to enumerate as a USB mass storage device.
2. Copy the files loader.uf2, xous.uf2, and swap.uf2 to the device.
3. If you're under Linux, be sure to unmount the drive to ensure that the cached files are actually written to the device.
4. Press any button to boot the device.

This final boot step is required to flush any partially written sectors to disk; shutting off the device without booting can lead to a portion of the last sector going missing, depending upon the OS.
